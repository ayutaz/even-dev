## 3. 解く課題

原案（即売会向け）の課題設定を展示会向けに読み替える。解くのは「見たいブースがわからない」ことではなく、**会場内での最後の確認操作がスマートフォン向けに最適化されていない**ことである。

- 約 300 組・3,000 人規模の会場で、次にどのブースへ行くかを都度スマートフォンで確認するのは煩わしい。
- 展示を見ながら、デモを触りながらでは両手がふさがる。
- 会場の通信状態に依存したくない。
- 「次にどのブースか」「そこで何を見たいか」「残り何件か」だけを一瞬で確認したい。

価格・残予算は原案の柱だったが、本イベントは入場無料で物販が主目的ではないため中核から外す。

## 4. 想定利用者

Even G2 を所有する来場者。ただし来場者 3,000 人に占める G2 所有者は極めて少数と見込まれる。実利用者数を成功指標に置かず、次を目的とする。

- 主催が公式に G2 対応アプリを用意したという事実そのもの（AI・ハードウェア展示会との親和性）。
- Even Hub ストアへの掲載実績。
- 開発者自身および出展者による当日の実利用。

## 5. 機能要件

### 5.1 スマートフォン側（事前準備）

- 出展者一覧から、見たいブースを選んで巡回リストに追加する。
- 巡回リストの並び順を決める（追加順、またはブース番号順への並べ替え）。
- 各項目に「何を見たいか」のメモを付ける。
- リストを端末内に保存する（`localStorage`。`apps/garbage_cue` と同じ方式）。
- G2 未接続時はブラウザ上でプレビュー表示し、単体で動作を確認できる。

### 5.2 G2 側（会場での利用）

- 次に行くブース番号、出展名、見たいものを表示する。
- 残り件数を表示する。
- スクロールで項目を送る。
- タップで「訪問済み」を記録する。
- 完全オフラインで動作する。

## 6. 非機能要件

- **オフライン必須**。会場の通信状態を前提にしない。
- **審査対応**。個人情報・マイク・位置情報・外部アカウント・サーバー保存をいずれも使わない。これによりプライバシーポリシーを最小の記述で成立させる。
  - 唯一の外部通信は、公開されている出展者データ JSON の取得（読み取り専用の GET）である。ユーザーが作成した巡回リスト・メモ・訪問済み状態を外部に送信することはなく、すべて端末内に留まる。この通信は失敗しても機能に影響しない（10.3 を参照）。
- Even Hub Developer Platform Terms のサポート対象外カテゴリ（金融、健康・医療、教育・訓練、インスタントメッセージ、子ども向け）に該当しない。
- 会場で画面を注視することが安全上問題になる場面を想定し、1 画面あたりの情報量を絞る。

## 7. スコープ外（初版）

会場マップ画像、出展者のロゴ・作品画像、GPS、通知、サーバー同期、複数端末間の同期、タイムテーブル連動、出展者間のメッセージング、会場配置に基づく最適順路の算出。

## 8. 合格基準

- 出展者一覧から 20 件程度の巡回リストを 10 分以内に作成できる。
- 初見のユーザーが説明 5 分以内に「表示・訪問済み・次へ」を操作できる。
- 30 分の連続利用で、状態の取りこぼしと二重の訪問済み登録が 0 件である。
- 機内モード（完全オフライン）で基本操作が完結する。
- G2 実機でブース番号と出展名が判読できる。

## 9. 決定事項

| 論点 | 決定 |
| --- | --- |
| 出展者データの配布 | ビルドに同梱し、起動時に公式 URL から最新版を取得できたら差し替える |
| G2 の画面構成 | 1 件集中型（現在の 1 件だけを大きく表示） |
| G2 の操作割り当て | 下スワイプ＝次、上スワイプ＝前、シングルタップ＝訪問済みトグル、ダブルタップ＝終了 |
| 巡回順 | 既定はユーザーの追加順。スマートフォン側にブース番号順への並べ替えを用意 |
| 送り対象 | 全件を順送りする（訪問済みを飛ばさない） |
| アプリの位置付け | 汎用設計＋ Vol.6 データ同梱。名称は `EventLens` を継続 |
| テスト | Vitest を本アプリ内に導入し、純粋ロジックのみ対象とする |
| 同梱データの読み込み | `public/` への配置と `fetch` をやめ、`src/` に置いて `import` する（10.1 の理由を参照） |
| 長い出展名 | G2 では表示幅に合わせて切り詰め、`…` を付す。ブース番号は切り詰めない（10.4） |
| 型チェック | `apps/eventlens` にのみ `tsconfig.json` を置く。リポジトリには従来 1 つも無く、`npx tsc --noEmit` が実質何も検証していなかった |

## 10. 設計

### 10.1 ファイル構成

```
apps/eventlens/
  app.json / index.html / package.json / README.md
  vite.config.ts / vitest.config.ts / tsconfig.json
  src/
    exhibitors-data.json  同梱する出展者データ（import してバンドルに含める）
    main.ts             スマートフォン側 UI（一覧・選択・並べ替え・メモ）
    eventlens-app.ts    G2 コントローラ（SDK 描画とイベント処理）
    itinerary.ts        純粋ロジック：巡回リスト・訪問済み・カーソル
    exhibitors.ts       純粋ロジック：データ正規化・版数マージ・ソート
    remote.ts           純粋ロジック：更新取得（タイムアウト付き、例外を投げない）
    storage.ts          localStorage 入出力
    styles.css
    exhibitors.test.ts / itinerary.test.ts / storage.test.ts / remote.test.ts
```

`apps/garbage_cue` の 3 層構成（UI / G2 コントローラ / 純粋ロジック）を踏襲しつつ、テスト対象になる純粋ロジックを `exhibitors` `itinerary` `storage` `remote` に分離する。

同梱データを `public/` ではなく `src/` に置き、`fetch` ではなく `import` で読み込む。実装中に、`public/` 方式では**シミュレータ経由で起動したときに 404 になる**ことが判明したためである。スタンドアロンの開発サーバは `root` が `apps/eventlens` なので `public/` を配信するが、`start-even.sh` が使うルートの開発サーバは `root` がリポジトリルートであり、`apps/eventlens/public/` を publicDir として扱わない。`import` にすれば Vite がバンドルへ取り込むため、起動方法にも配信構成にも依存しなくなる。

なお `tsconfig.json` はこのアプリにのみ置く。リポジトリには従来 `tsconfig.json` が 1 つも存在せず、`npx tsc --noEmit` が対象ファイルを 1 つも拾わない状態だったため、型チェックが実質機能していなかった。

### 10.2 データモデル

```ts
type Exhibitor = { id: string; booth: string; name: string; genre?: string }
type EventData = {
  eventId: string; eventName: string; eventDate: string
  version: number; exhibitors: Exhibitor[]
}
type ItineraryItem = { exhibitorId: string; note: string; visited: boolean }
type SavedState = { eventId: string; items: ItineraryItem[]; cursor: number }
```

`id` を安定キーにすることで、データを差し替えてもユーザーのメモと訪問済み状態が保持される。汎用設計は `eventId` によって成立する。

### 10.3 データフロー

1. 起動時に同梱データ（`src/exhibitors-data.json`）を `import` で読む。ネットワークも開発サーバの配信構成も介さないため、この段階で失敗する経路がない。
2. `localStorage` に保存済みの更新データがあれば `version` を比較し、新しい方を採用する。
3. 公式 URL からの更新取得をタイムアウト付きで試行する。失敗は無視して続行する（オフライン要件）。
4. 巡回リストを復元し、`exhibitorId` で出展者を解決する。
5. G2 に接続し、現在項目を描画する。以後はイベント受信ごとに状態を更新し、再描画して即保存する。

状態は操作のたびに保存する。合格基準の「30 分連続で取りこぼし 0 件」は、途中終了やアプリ切り替えを挟んでも状態が残ることを要求するためである。

### 10.4 G2 の画面と操作

1 画面に現在の 1 件だけを表示する。

```
  B-12
  ずんだもん研究所

  音声合成デモを触る

  未訪問  残り 8 / 20  (3/20)
  ↑↓送り  タップ=訪問済  2回タップで終了
```

**確定したコンテナ配置**（描画領域は 560×266）

| ID | 役割 | x | y | 幅 | 高さ | `isEventCapture` |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | ブース番号＋出展名 | 8 | 4 | 544 | 100 | 0 |
| 2 | メモ | 8 | 108 | 544 | 40 | 0 |
| 3 | 状態・残り件数・操作ヒント | 8 | 152 | 544 | 40 | 0 |
| 4 | 巡回リスト（イベント捕捉用） | 8 | 196 | 544 | 70 | 1 |

幅を 560 ではなく 544 にしたのは、`xPosition: 8` と合わせると `x + width` が 568 となり描画領域を 8px 超えるためである（`apps/garbage_cue` は同じ超過を抱えている）。左右 8px の対称マージンになる。

**イベント捕捉にリストコンテナが必要である。** この SDK ではジェスチャーがリストコンテナにしか届かないため、1 件集中型の画面でもリストを 1 つ置く必要がある（`apps/timer` も同じ理由で捕捉専用のリストを持つ）。テキストコンテナは `isEventCapture: 0` とする。

| 操作 | 動作 |
| --- | --- |
| 下スワイプ（`SCROLL_BOTTOM_EVENT`） | 次の項目へ |
| 上スワイプ（`SCROLL_TOP_EVENT`） | 前の項目へ |
| シングルタップ（`CLICK_EVENT`） | 訪問済みをトグル |
| ダブルタップ（`DOUBLE_CLICK_EVENT`） | 終了 |

訪問済みをトグルにすることで、誤操作の取り消しを別 UI なしで解決する。訪問済みの項目はスクロールで戻れば表示され、マーク付きで区別される。

なお `apps/_shared/even-events.ts` の定義どおり、取得できるイベントは `CLICK` / `SCROLL_TOP` / `SCROLL_BOTTOM` / `DOUBLE_CLICK` の 4 種である（`apps/timer` は CLICK で開始、DOUBLE_CLICK で停止という使い分けをしている）。ダブルタップを終了に割り当てるのは `apps/garbage_cue` と `apps/restapi` の慣習に合わせたものである。

**カーソルはスクロールイベントだけで動かす。** リストは選択位置を報告してくるが、SDK には選択位置を*書き込む*フィールドが無い。端末が報告する位置を採用すると、アプリ側が独自にカーソルを動かしたとき（保存状態からの復元、ブース番号順への並べ替え、項目の削除）に端末とずれ、次のスワイプで表示が飛ぶ。真実源を `main.ts` の 1 つに保つため、端末の報告値は使わない。

**長い出展名は切り詰める。** 行高の実測値（13 を参照）から、高さ 100 の見出しに入るのは 3 行、うち 1 行はブース番号が使うため、名前に使えるのは 2 行 = 72 カラムである。同梱サンプルの最長は 80 カラムあり、そのままでは溢れてメモ行と衝突する。`truncateToColumns` で 72 カラムに収め、末尾に `…` を付す。リスト行は 1 行なので 36 カラムに収める（`✓ ` の訪問済みマークも予算に含めるため、組み立ててから切り詰める）。**ブース番号は会場での識別子なので切り詰めない。**

### 10.5 エラー処理

| 事象 | 挙動 |
| --- | --- |
| G2 未接続 | ブラウザプレビューに切り替える（`apps/garbage_cue` と同一の方式） |
| 更新取得の失敗・タイムアウト | 静かに同梱データで続行し、ログのみ残す |
| `localStorage` の破損 | 初期状態にフォールバックし、クラッシュさせない |
| 更新で出展者が消えた | 項目を消さず「掲載終了」表示で残し、ユーザーのメモを失わせない |
| 巡回リストが空 | G2 に「スマホでリストを登録してください」と表示する |
| 接続後の描画に失敗 | 登録済みのイベントリスナーを解除してから状態を戻す |

最後の 1 行は実装中に判明した不具合への対処である。`onEvenHubEvent` は解除関数を返す加算型の登録であり、これを捨てたまま再接続するとリスナーが二重に登録される。その状態ではタップ 1 回で訪問済みが 2 回反転し、**操作しても何も起きないように見える**（エラーも出ない）。解除関数を保持し、再登録の前と接続失敗時に呼ぶ。

### 10.6 ローカル実行とデバッグ

開発とデバッグは Even G2 実機ではなく **Even Hub Simulator** を主軸に行う。`apps/eventlens/` をリポジトリの規約どおりに作れば `start-even.sh` が自動検出するため、ランチャー側の変更は不要である。

| 目的 | コマンド |
| --- | --- |
| G2 シミュレータで動作確認（主） | `./start-even.sh eventlens` |
| ブラウザ単体で UI を確認 | `cd apps/eventlens && npm run dev`（ポート 5180） |
| ロジックのテスト | `cd apps/eventlens && npm test` |
| 審査提出物の生成 | `./scripts/pack-app.sh eventlens` → `apps/eventlens/out.ehpk` |

ポート 5180 は空き番である（5174 timer / 5175 base_app / 5176 hello_world・restapi / 5177 quicktest / 5178 clock / 5179 garbage_cue）。

開発は次の 3 段で進める。

1. **Vitest** — 純粋ロジック（巡回順、訪問済みトグル、残り件数、版数マージ）を機械的に検証する。
2. **シミュレータ** — 表示と操作を検証する。実機がなくても以下を確認できる。
   - 1 件集中型レイアウトの可読性（幅 560 での日本語の折り返し、長い出展名の扱い）
   - 4 種の操作イベントが期待どおり届くか
   - 約 300 件のデータを読み込んだ状態での描画と状態遷移
3. **実機** — 合格基準「G2 実機でブース番号と出展名が判読できる」の最終確認のみ実機で行う。

### 10.7 テスト

Vitest を `apps/eventlens` 内に限って導入する。対象は純粋ロジックのみとし、SDK ブリッジと DOM は対象外とする（それらはシミュレータで確認する）。

**確定した内訳：計 82 件**

| ファイル | 件数 | 主な対象 |
| --- | --- | --- |
| `exhibitors.test.ts` | 38 | 正規化、版数マージ、消えた出展者、**ブース番号の自然順ソート**（`B-2` < `B-12`。辞書順では逆になる）、表示幅の計算と切り詰め |
| `itinerary.test.ts` | 24 | 追加・削除、並べ替え、訪問済みトグル、カーソル移動と端の折り返し、残り件数 |
| `storage.test.ts` | 14 | 破損データからの復帰、範囲外カーソルの丸め、ストレージ例外の握り潰し |
| `remote.test.ts` | 6 | HTTP エラー・通信例外・不正 JSON・タイムアウトのいずれでも `null` を返すこと |

テスト対象を増やすため、`localStorage` に触る関数は `StorageLike` を第 1 引数で受け取り、モジュール内部で `window` を参照しない設計にした。同じ理由で、切り詰めロジックは G2 コントローラではなく `exhibitors.ts` の純粋関数として実装している。

## 11. 残っている作業

コードは完成している。以下は主催側の作業であり、コードの完成とは独立している。

1. **出展者データの差し替え** — 現在は架空のサンプル 24 件が入っている。`apps/eventlens/src/exhibitors-data.json` を実データに更新し、`version` を上げる。**ブース番号は半角数字で入力する**（全角数字は数値として扱われず、該当ブースが並べ替えの末尾に落ちる）。データはビルド時にバンドルへ取り込まれるため、差し替えには再ビルドが必要である。
2. **更新用 JSON の配置（任意）** — 同じ JSON を `main.ts` の `REMOTE_DATA_URL`（既定は `https://www.genai-expo.com/eventlens/exhibitors.json`）に置くと、通信できる端末は起動時に新しい `version` を取得する。公開後のデータ更新を再提出なしで反映できる。URL を変える場合は定数を修正する。
3. **プライバシーポリシーの掲示先 URL** — Even Hub の公開審査に必要。`app.json` には該当フィールドが無いため、提出フォーム側で入力するものと思われる。内容は「巡回リスト・メモ・訪問済み状態は端末内にのみ保存し、外部送信しない。出展者データの取得のみ通信を行う」で足りる。
4. **審査提出** — `./scripts/pack-app.sh eventlens` が生成する `apps/eventlens/out.ehpk` を提出する。目標日は 2026-09-01。
5. **実機での可読性確認** — 合格基準のうち「G2 実機でブース番号と出展名が判読できる」のみ実機を要する。

## 12. 主なリスク

- Even Hub の公開審査期間が不確定であり、開催日までに公開できない可能性がある。
- 来場者の G2 所有者が極めて少なく、実利用者が一桁にとどまる可能性がある。
- 出展者一覧が開催直前まで確定せず、同梱データの差し替えが間に合わない可能性がある。
- 会場での G2 表示が、運営ルールや安全上の問題になる場面がありうる。
- G2 実機での日本語フォント、ブース番号、出展名の可読性が未検証である（レイアウトは 13 の実測値に基づいて設計したが、実機での確認は未実施）。
- 出展者名に絵文字が含まれると表示幅の計算が過小になる（`displayColumns` の対象範囲に絵文字ブロックを含めていない）。実データは主催側が用意するため現状のリスクは低い。

## 13. 実装から得た知見

設計時には分からず、実装中に判明した事実を記録する。同種のアプリを作るときに再び必要になる。

### 13.1 G2 のテキスト表示寸法

SDK はフォントサイズも行高も公開しておらず、指定もできない（`TextContainerProperty` にそれらのフィールドが存在しない）。表示寸法は端末側の固定値であり、既存アプリのコンテナ寸法から逆算するしかない。

| 出典 | 根拠 | 導かれる値 |
| --- | --- | --- |
| `apps/restapi/src/restapi-app.ts:55` | `GLASS_RESPONSE_WRAP_WIDTH = 38`（幅 560 のコンテナに 38 カラムで折り返す） | 幅 560 で **38 カラム**、1 カラム ≒ 14.7px |
| `apps/restapi/src/restapi-app.ts:446-451` | 応答本文が `height: 198` で `maxLines: 8` | 1 行 ≒ **24.75px** |
| `apps/restapi/src/restapi-app.ts:493-498` | 状態表示が `height: 62` で 2 行 | 1 行 ≒ **31px** |

行高は 24.75〜31px の幅がある。安全側の 31px で設計した。全角文字は 2 カラムとして数える。幅 544 なら 1 行あたり約 36 カラム（全角 18 文字）である。

### 13.2 `app.json` のスキーマ

`evenhub-cli` が `pack` 時に検証する内容は文書化されていない。バリデータから読み取った現行の要件は次のとおり。

- `permissions` は **`{name, desc}` オブジェクトの配列**。`name` の有効値は `g2-microphone` / `phone-microphone` / `album` / `location` / `network` / `camera` の 6 種のみ。`desc` は最大 300 文字。
- **通信先ホストを列挙するフィールドは存在しない。** 審査担当に通信先を伝える手段は `desc` の本文だけである。
- `min_sdk_version`（文字列）と `supported_languages`（`en` `de` `fr` `es` `it` `zh` `ja` `ko` のみ）は必須。欠けると `pack` が失敗する。

**`apps/timer` と `apps/restapi` の `permissions: {"network": [...], "fs": [...]}` という形式は現行 CLI では検証に通らない。** 新規アプリはそれらを手本にしないこと。

### 13.3 開発サーバの `root` が起動方法で変わる

`cd apps/<name> && npm run dev` は `root` が `apps/<name>` なので `public/` を配信するが、`./start-even.sh <name>`（シミュレータが使う経路）はルートの `vite.config.ts` が動き `root` がリポジトリルートになるため `apps/<name>/public/` を配信しない。

`public/` のデータを `fetch` する実装は、スタンドアロンでは動くのにシミュレータでは 404 になる。しかも `npm run build` では `public/` が `dist/` にコピーされるため、パッケージ版と実機では動いてしまい、**開発時だけ壊れる**。同梱データは `src/` に置いて `import` するのが安全である。

この不具合は単体テストにも差分レビューにも引っかからず、シミュレータを実際に起動して初めて発見できた。
